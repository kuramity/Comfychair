# 预置工作流规范

> 适用范围：`app/src/main/assets/prebuilt_workflows/` 下的预置工作流。
> 每次新增/修改预置流后，跑一遍体检脚本再交付。
> 建立于 2026-09-12，来源是几轮真实故障的复盘。

## 一、先跑体检

新增/修改预置流后，按下文「检查项」逐条自查（A/B/C/E 是明确缺陷，交付前必须为 0）。

```bash
# 至少在 App 里导入一次、确认占位符能被识别与替换：
# 导入 → 打开参数面板 → 看模型/图片/提示词各类控件是否都有值且能修改
```

检查项：

| 编号 | 内容 |
|---|---|
| A | 用了 App 不支持的占位符（拼错，或该字段 App 根本不会替换） |
| B | 尺寸机制与工作流类型不符（编辑模式用了 `width`/`height`） |
| C | 图生图/图生视频缺图片占位符；或文生类带了图片占位符 |
| D | 提示词内嵌在节点里（App 里填的会被丢弃） |
| E | 归类为文生图/文生视频但没有采样器（不具备生成能力，归类多半有误） |

## 二、五条硬规则

### 1. 归属的类型必须与工作流真实能力一致

类型决定 App 用哪套界面与哪条替换路径。**类型错了，接口就对不上。**

| 类型 | 界面上用户能做什么 | 工作流必须有什么 |
|---|---|---|
| `TTI` | 填提示词 | 采样器 + 潜空间 + 解码器；**没有图片上传入口** |
| `TTV` | 填提示词 | 同上（视频） |
| `ITI_EDITING` | **传图** + 填提示词 | 从图片输入起步（放大/修复/编辑类可以没有采样器） |
| `ITV` | 传图 + 填提示词 | 视频生成 |

> 踩过的坑：`Pornmaster Z-Image Turbo_t2i` 全部 17 个节点里没有采样器，实际是"传图 → 人脸修复 → 保存"，
> 却归成了 `TTI`。用户既没法传图、`{{image_filename}}` 也不会被替换，直接失败。

### 2. 用户在 App 里能调的字段，必须有对应占位符

漏占位符 = 用户填了也没用，**而且不会报错**（静默用旧值），最难排查。

> 踩过的坑：MiniMaxH3 的四个视频流（图生视频/文生视频/首尾帧/多参）提示词全部写死在
> `MiniMaxH3ImageToVideo.prompt` 里，用户在 App 里改提示词毫无效果，每次出图都用同一份旧提示词。

做法：**替换成占位符的同时，把原值写进 `defaults`**，这样 App 打开该流时会预填，
用户能看到并修改，而不是面对一个空框。

已在 App 端实现的替换路径（`WorkflowManager`，按函数区分）：

| 占位符 | 会被替换的路径 |
|---|---|
| `positive_prompt` / `negative_prompt` | TTI、TTV、ITI（修补+编辑）、ITV 全覆盖 |
| `image_filename` | **仅图生图/图生视频**（`prepareImageToImageWorkflowById`、`prepareImageEditingWorkflowById`、`prepareImageToVideoWorkflowById`） |
| `width` / `height` | 生成类（TTI/TTV/ITV） |
| `megapixels` | 编辑类（ITI_EDITING/INPAINTING） |
| 模型类（`unet_name`/`vae_name`/`clip_name`/`lora_name` 等） | 全路径 |

### 3. 尺寸机制不能混用

- **生成类**（TTI/TTV/ITV）：用 `{{width}}` / `{{height}}`
- **编辑类**（ITI_EDITING / INPAINTING）：用 `{{megapixels}}`

编辑模式按源图比例缩放到目标像素量，它的替换函数**不接受** `width`/`height` —— 写了也不会被替换，
字面量直接发给服务器，报 `Failed to convert an input value to a INT value`。

> 踩过的坑：`Krea2-高清重绘` 归类为图生图、却用了 `{{width}}`/`{{height}}`，
> 提交必然 400。它其实与 `Krea2-初生图`/`二采出图` 同族、都是纯文生图（源工作流也没有图片输入节点）。

### 4. 一个流只能有一个输出节点

`SaveImage` 与 `PreviewImage` **都算输出节点**，两者加起来必须恰好 1 个。

App 的取图逻辑是「遍历 `/history.outputs`，取**第一个**有 images 的节点的**第一张**」，
另有 WebSocket 即时取图链路。多一个输出节点不是报错、而是**随机取到某一张** ——
用户看到的是低清预览图或半成品，且完全不可复现。

做法：
- 中间产物一律删掉，或在预置流里根本不保留（桌面上用于肉眼比对的 `PreviewImage` 要剔除）；
- 需要"先看中间结果"的流，把原存图节点**改接**到最终结果上，**不要新增**存图节点；
- 契约测试逐资产断言 `SaveImage + PreviewImage == 1`（`HiresPrebuiltContractTest`）。

> 踩过的坑：Krea2 极清流的桌面版有 3 个 `SaveImage`（中间存图）与 1 个 `PreviewImage`，
> 直接转换会让用户拿到一采的低清图。历史上 `prebuilt_02`（3 预览 + 1 存图）、
> `prebuilt_05`（预览 + 存图）也是多输出，尚未清理。

### 5. 多阶段采样用「阶段前缀」分组

同一台采样器内部的多个阶段、或串联的多台采样器，参数用**阶段前缀**命名，
App 的 `SamplerStageRegistry` 据此把控件归入「阶段 N」卡片并换中文标签：

| 前缀 | 阶段 | 用在哪 | 参数名 |
|---|---|---|---|
| `comp_` / `struct_` / `detail_` | 1 / 2 / 3 | 竖叉流（`IllustriousTriplePassSampler` 一张节点统合三阶段） | `steps` `cfg` `denoise` `sampler` `scheduler` |
| `stage2_` | 2 | 没有前缀可依的第二个采样器（Krea2 二采） | 同上 |
| `hires_` | 4 | 放大之后的补采与预放大倍数（v0.9.23 新增；**分次补采的开关/步数/强度带轮次后缀**，如 `hires_on2`、`hires_steps1`） | 同上，外加 `scale`（`ImageScaleBy.scale_by`）与轮次后缀参数名 `on1..3` / `steps1..3` / `denoise1..3` |

**新前缀要三处同时登记**，缺一处就静默失败：

1. `app/src/main/java/sh/hnet/comfychair/workflow/dynamic/SamplerStageRegistry.kt` 的 `KNOWN` / `PARAM_KEYS`
2. `res/values/strings.xml` 与 `res/values-zh/strings.xml` 的阶段名与参数标签
3. `verify_prebuilt_mapping.py` 的 `STAGE_PREFIXES` / `STAGE_PARAMS`（不登记会被判成"凭空写的占位符"）

`hires_*` **不属于** `TemplateKeyRegistry` 的"已识别占位符"，替换由**通用节点参数引擎**
（`DynamicParamScanner → DynamicParamTypeResolver → DynamicParamValues`）完成 —— 这是刻意的：
通用引擎在全部 5 条替换路径上都生效，而已识别占位符各有各的专用路径
（例如 `scale_by` 只在 TTI 路径被替换，编辑类路径不会）。

> 阶段参数是**全局同名文本替换**：同一个占位符名只能出现在一处目标上。
> 一条流里有多个 `VAELoader`／`UNETLoader`／采样器时，非目标的那些必须**写死字面量**
> （Krea2 极清流里 SeedVR2 的两个加载器与那台 1 步采样器就是写死的）。

## 三、转换时的注意事项

转换脚本（`convert_prebuilt.py`）靠**标准采样器的 positive/negative 输入**定位提示词节点。
用自定义节点的流（如 MiniMaxH3 系列）会**整个漏掉**，转换后必须人工确认提示词是否已做占位符。

同理，源工作流里被 bypass 的节点，转换时会恢复成启用 —— 如果某条链依赖外部输入
（如人脸修复要读上传图），恢复启用后可能让工作流无法运行，需要单独判断。

## 四、已知的有意例外

- `prebuilt_03`（简单 4x 放大）、`prebuilt_07`（MiniMaxH3 四视图）：提示词**有意内嵌**，
  用户明确要求免填。它们列在体检脚本的 `INTENTIONAL_INLINE_PROMPT` 白名单里。

## 五、极清放大系列（v0.9.23 新增）

| 资产 | App 名 | 类型 | 说明 |
|---|---|---|---|
| `prebuilt_19_krea2_extreme_hires.json` | Krea2-极清生图流 | `TTI` | 桌面四段（一采 → 潜空间二采 → `UltimateSDUpscale` 分块重绘 → `SeedVR2-3b` 放大）**重连为端到端单次出图**。默认 768×1344，最终约 1728×3024 |
| `prebuilt_20_seedvr2_3b_upscale.json` | SeedVR2-3b图像放大 | `ITI_EDITING` | 传图 → `ImageScaleBy` → SeedVR2 预处理/1 步整流采样/后处理 → 智能锐化。默认 2.0 倍，1024×1536 输入得 2048×3072 |
| `prebuilt_21_zimage_seedvr2_hires.json` | Z-Image-极清整合流 | `TTI` | 文生图（Turbo 8 步）→ 自动修脸 → 预放大 → SeedVR2-3b int8 还原式放大 → 智能锐化，一次提交出高清成品。默认 1024×1536 出 2048×3072；显存不够时先调小分辨率或「预放大倍数」。 |
| `prebuilt_11_shucha.json`（改造） | illustrious-Noob AI（不变） | `TTI` | 三阶段采样之后追加「4× 动漫放大 → 缩到 2 倍」+ **可开关的 1~3 次补采**（默认全关）。1024×1536 出 2048×3072；默认档实测 42 s，开 1/2/3 次为 73 / 81 / 89 s |

要点：

- 资产由 `build_hires_prebuilts.py` **直接构造**（唯一写入口，幂等：重复运行逐字节一致）。
  **不要**重跑 `convert_prebuilt.py`（它只覆盖 01~16、会抹掉 05/06 的 `{{upscale_model}}`，
  且注入占位符是启发式的，在多加载器/多采样器流上会选错节点）。
  也不要让 `inject_stage_placeholders.py` 的 `DESCRIPTIONS` 重复登记 19/20/21（避免两个写入者）。
- **`prebuilt_21` 的 `CLIPLoader.type` 必须是 `qwen_image`，不是 `flux2`**（2026-09-23 实测定案）。
  本机 ComfyUI 0.34.0 的 `comfy/sd.py` 在 `te_model == QWEN3_4B` 时：`type in (flux, flux2)`
  → `flux.klein_te()` + `KleinTokenizer`（Flux2-Klein 分支，TE 取 `layer=[9,18,27]` 三层拼接 →
  `[1,512,7680]`），**否则** → `z_image.te()` + `ZImageTokenizer`（单层 `layer_idx=-2` → `[*,2560]`）。
  选 `flux2` 会在 `KSamplerAdvanced` 直接炸：
  `RuntimeError: Given normalized_shape=[2560], expected input with shape [*, 2560], but got input of size[1, 512, 7680]`。
  旧记忆「Z-Image 必须选 flux2」对应的分支顺序已在本机版本改变 —— **以实测为准**。
  判据不只"出图成功"：`comfyui.log` 里 `Requested to load ZImageTEModel_`（正确）
  vs `Flux2TEModel_`（错误分支）可一眼分辨。
- **`prebuilt_21` 的节点数不得低于 25**：它同时含主干 `98` 与 SeedVR2 `240` 两个 `UNETLoader`，
  而 `LoraInjectionUtils.findModelSourceNode()` 取"`org.json` 的 `HashMap` 迭代顺序里第一个 `UNETLoader`"。
  26 节点 → 容量 64 → 桶位 `98`=31 先于 `240`=46（落点正确）；**掉到 ≤24 → 容量 32 →
  桶位变成 31 / 14 → 落点翻转到 SeedVR2**（用户加的 LoRA 静默挂到放大模型上，主模型没有 LoRA 且不报错）。
  所以主干那两个死端节点（`151 easy cleanGpuUsed` / `152 PlaySound|pysssss`）**必须保留**。
  双保险：文档顺序里 `98` 也写在 `240` 之前。改这些 id 必须同步
  `ZImageHiresMergeContractTest.LoRA 链注入落在主干 98 而不是 SeedVR2 240 且节点总数在 25 到 48 之间`。
- **SeedVR2 的 VAE 需要用户手动复制**：`models\SEEDVR2\ema_vae_fp16.safetensors` →
  `models\vae\seedvr2_ema_vae_fp16.safetensors`（零下载）。
  `VAELoader` 只扫 `models\vae\`，官方节点包的 `SeedVR2LoadVAEModel` 输出 `SEEDVR2_VAE` 类型，
  只有 `SeedVR2VideoUpscaler` 接受，而后者的 `SeedVR2LoadDiTModel` 下拉里没有 3B int8 convrot —— 无替代路线。
- 桌面用 `ResizeImageMaskNode` 做预放大的一律换成经典节点
  `ImageScaleBy(image, upscale_method="lanczos", scale_by=N)`：前者在本机 0.34.0 已改成
  V3 动态组合节点，桌面保存的是旧签名，API 格式能否直接提交未经证实。
- 耗时口径：`KSampler` 的 NFE 次数 = `steps`，**与 `denoise` 无关**（`set_steps()` 只决定从噪声表哪一段起跑）。
  「steps × denoise 当量」的估算是错的。
- **竖叉流（`prebuilt_11`）的补采：默认关闭 + 可选 1~3 次**（2026-09-22 用户口径，沿革见下）。
  现行实测口径（1024×1536 → 2048×3072、分块 VAE）：**全关 42.4 s / 补采 1 次 72.6 s /
  2 次 81.4 s / 3 次 88.8 s**；改造前是 36.2 s，即默认档 **+17%（+6.2 s）**。
  补采段的固定开销 ≈ 21 s（6.29 MP 的 VAE 往返 + `KSampler` 启动），此后**每步 ≈ +3 s**。
  > **沿革（旧数字勿再引用）**：更早一轮是**整图 VAE** 测的：36.2 s → 45.2 s（+25%）→
  > 补采 1 步 96.4 s / 3 步 130.9 s、"每步 +17 s"，并据此删过一次补采。Fix Round 2 查明
  > 那 +17 s/步 的大头是 6.29 MP 上的显存换页（整图 VAE 114.4 s vs 分块 71.1 s），
  > 不是采样本身，于是改回"保留但默认关闭"。
  > 实现要点：4 个 `CRZSwitch`（惰性开关）做轮次开关与总闸，`hires_on1` 兼总开关；
  > 潜空间串联共用一趟 VAE 往返。**开关必须是 `lazy` 节点**，否则"关"只是"跑了不用"。
  > 注意「关掉」**只免执行、不免服务端校验**：越界值仍会让整单 400（见下一条）。
- **数值参数的范围校验**（2026-09-22 Fix Round 3）：`/object_info` 里的 `min` / `max` 现在真的被用起来 ——
  面板里越界即时标红并写明"生成时会自动取 N"，提交前再把越界值夹到最近的合法值
  （`app/src/main/java/sh/hnet/comfychair/workflow/dynamic/DynamicParamRange.kt`，纯逻辑、有单测）。
  起因：服务器 `validate_inputs()` 沿**全部连线**递归校验，`lazy` 只影响执行表 ——
  把 `hires_steps1` 改成 0（哪怕补采三个开关全关）照样整单 400 `value_smaller_than_min`。
  当前全部预置资产里带范围的动态参数都落在没有 `VALIDATE_INPUTS` 的节点上，夹紧不会误伤。
- 降级顺序（每级只动一个值）：App 分辨率调小 → 生成脚本切
  `KREA2_VARIANT = "no_seedvr2"`（Krea2 流去掉 SeedVR2 段）。竖叉流的补采默认即为关闭档，
  需要更快时保持关闭、或调小 `hires_scale`。
