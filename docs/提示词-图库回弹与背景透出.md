### 2.5 我的怀疑清单（你自己判断，不要照抄）

**H1：`leavePages` 全是 0.0，说明"冻结位移"没生效。**
`frozenLeavePages` 的设计是"松手瞬间（`DragInteraction.Stop`）冻结 `currentPageOffsetFraction`"，因为框架在 `calculateTargetPage` 之前会把偏移吸收为 0。
日志里 8 次全是 0.0，而 `totalDx` 显示手指确实拖出了 200~380px（0.19~0.35 页）。**要么冻结没触发、要么冻结的值被提前清掉、要么读取的时机不对。**
→ 请查 `frozenLeavePages` 的赋值与清除时机，并在每帧打日志证明它到底有没有值。

**H2：`target` 返回正确但 fling 动画没执行。**
`suggested=2 → target=2` 是正确结论，但 `startPage` 8 次都是 1。这说明"判定对了，动画没跑"或者"动画被下一次手势取消"。
→ 请验证：`PagerDefaults.flingBehavior(snapAnimationSpec = spring(250, NoBouncy), decayAnimationSpec = maxDistanceDecaySpec)` 在这条路径上到底有没有产生动画。怀疑点是 `decayAnimationSpec` 在 `velocityPxPerSec` 被归零时的行为（`MaxDistanceDecaySpec` 的 KDoc 自己写着"全屏态 approach 段被短路"）。
→ 也请检查 `snapAnimationSpec` 用 `spring` 而不是 `tween` 是否与 `visibilityThreshold` 有关（v4.22.1 刚从 tween 换成 spring）。

**H3：第 0 步（快甩翻一页）的 `MIN_FLING_LEAVE_FRACTION` 门槛导致"拖一点点就多翻一张"。**
`leavePages=0.1787 / 0.1092` 时 `target = suggested + 1`。也就是 10%~18% 的位移就被判成"要翻页"。用户的直觉阈值是"过半才翻"。
→ 请核对这几个常量的取值与设计意图，判断 0.1092 这种值该不该触发"快甩"。

**H4：pager 的 `userScrollEnabled` / 其他手势抢占了 fling。**
`ImageViewer` 里可能有 `detectDragGestures`（下滑关闭、捏合、双击缩放）与 pager 的 drag 竞争。若某个手势在 `onDragEnd` 里做了 settle 或者取消了 pager 的 fling，就会出现"判定对了但页面不动"。
→ 请检查 `ImageViewer.kt` 的手势优先级与 `pagerState` 的交互。

**H5：三处状态机互相打架。**
`displayPageFraction`（G3）、`ViewerOverscroll`（G1 越界位移）、`ViewerSideBySide`（并排档位）三条位移通道"互不越界"是**设计契约**（见 `ViewerPageMotion.kt` 头部 KDoc）。如果其中一条在松手瞬间写了值，可能把 pager 拉回。
→ 请用日志证明松手瞬间到 settle 完成之间，有没有别的东西写了 `pagerState`。

## 3. 问题 B：全屏查看器背景透出图库网格（竖图两侧露边时）

### 3.1 用户原话

> 图库如果有未加载的图片，那么在他旁边的已经加载好的图片进入单图全屏后，会有旧的问题出现——加载好的图片占据多于 50% 半边屏，图库网格图就会透出。

截图佐证（我收到的）：全屏查看器打开后，**右侧约 2/3 是那一张大图，左侧约 1/3 直接显示图库网格（含一个正在转的加载 spinner 和几张缩略图）**，顶部有 `2 / 14` 计数器，底部有删除/保存/复制/分享/信息操作栏。也就是说查看器 UI 是在的，只是大图两侧露出了**图库画面**。

### 3.2 我读代码得到的因果链（这条我比较确信，但仍请你验证）

**① 查看器背景层用的是一张"图库整屏截图"**

`MediaViewerActivity.kt:37、93` 有 `gallerySnapshot`（图库整屏截图 Bitmap）+ `galleryCellRect`（被点格子的矩形），转场与"下拉透出"都靠它。

`MediaViewerScreen.kt:540-565`：

```kotlin

    Box(modifier = Modifier.fillMaxSize().graphicsLayer {
        alpha = if (sideProgress == 0f) 1f else 0f   // 全屏态 alpha=1，并排态才是 0
        translationX = overscrollPx

        Image(bitmap = snapshotBitmap, contentScale = ContentScale.FillBounds,
              modifier = Modifier.fillMaxSize())

    }
}
```

**② `revealActive` 在全屏态就为 true**

`MediaViewerScreen.kt:467-471`：

```kotlin

    gallerySnapshot != null && galleryCellRect != null &&
    revealItemKey != null && revealItemKey == entryItemKey &&
    revealItem.isVideo == false
```

只要"还停在进入时那一页"+不是视频，`revealActive` 就成立。**与是否正在下拉无关**。

**③ 根容器黑底画在截图层之下**

`MediaViewerScreen.kt:406-410`：

```kotlin

    // 内容（含上面的截图层）

```

`background` 是最底层的修饰符 → **截图层盖在黑底之上**。

**④ "满页黑"只在"无图/加载中"分支画，有图时不存在**

`MediaViewerScreen.kt:1755-1765`：

```kotlin

    // G1：只在全屏态需要——并排态的截图层已整层透明，背景由容器纯黑负责，

    }
    ...

```

这段在 `mode` 的 `else` 分支里，**图片正常渲染时走不到**。

**⑤ 竖图按 Fit 缩放，两侧必然留边**

日志里用户说全是 `1024×1536`（2:3 竖图）。屏宽 1080、屏高 2376：
- 高度撑满 2376 → 宽度 = 2376 × (1024/1536) = **1584 > 1080** → 实际会按**宽度**撑满或按高度撑满，取决于 `contentScale`

这里要你实测确认：**pager 页内图片到底用的是哪个 `contentScale`**（`MediaViewerScreen.kt` 里只搜到 :556 一处 `ContentScale.FillBounds`，那是截图层的；页内实际图片由 `ImageViewer` 组件画）。如果页内是 `Fit`，竖图两侧就会露出下面的截图层。

**⑥ 结论（待你验证）**

> 全屏态下，图库整屏截图的 alpha 恒为 1，画在纯黑之上；图片按比例缩放后两侧留出的空白区直接叠在截图上 → 用户看到"图库网格透出"。并把这张截图误认为"活的图库"（其实截图里那个 spinner 是拍截图那一刻的瞬时画面）。

### 3.3 为什么"有未加载的图片"时才明显

未加载的图片在截图里是**空占位格 + spinner**，视觉上和"活图库"几乎无法区分；已加载的缩略图则一眼就能看出来是图库。这是用户觉得"有未加载图片时才出现"的可能原因（也可能是别的原因，请自行验证）。

### 3.5 我的怀疑清单（你自己判断）

**H6：截图层应该只在"下拉透出"激活时可见。**
现在 `alpha = if (sideProgress == 0f) 1f else 0f` —— 全屏（sideProgress==0）时最不透明，恰好最该透明。设计意图可能是"全屏时截图当背景色用"，但截图是**图库画面**，不是纯黑。请确认这里的意图，并判断是否应改成"只有真的在下拉（`pullProgress > 0`）时才渐显"。

**H7：z 序错位。**
即使截图 alpha=1 是设计意图，纯黑也必须在**截图之上**才能兜住。现在黑在最底下，等于没有任何遮挡。

**H8：页内图片的 `contentScale` 不是 `Crop`。**
如果竖图用 `Fit`，两侧留边是正常排版；那么"露出截图"就必然发生。要么两侧铺黑（页内或页级），要么背景永远不显截图。
